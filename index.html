02 / Before Coding

开发前：把问题暴露在开发之前

需求理解不清会导致返工、联调反复、测试问题增多，甚至影响上线质量。AI 在这里承担的是需求收敛器和风险雷达。

自动分析需求文档

需求评审后，通过机器人自动提炼核心需求、拆解功能模块、识别风险点。

对话式持续澄清

通过一问一答逐步确认细节，避免一次性生成大量低价值文档。

规范化沉淀与协同

本地创建开发分支、生成规范文档，并在线沉淀技术方案，统一产品、后端和测试上下文。

核心目标：在正式开发前完成需求收敛与技术澄清，把后置返工变成前置发现。
03 / Design To Code

开发中：AI 辅助设计稿还原与代码生成

通用 Figma 转代码常常“能运行，但无法真正进入业务工程体系”。这里的关键是空间化重组、私有组件识别、工程规范落地与持续优化。

01

输入设计稿

批量读取 Figma 节点、页面信息、样式信息和资源信息。

02

设计稿解析

解析节点结构，补齐设计稿原始层级中不稳定的结构信息。

03

结构分析与优化

层级分析、冗余节点识别、结构压缩、节点重组、无效节点剔除。

04

组件识别与映射

识别团队私有组件，完成可扩展组件匹配与置信度评估。

05

样式转换与标准化

样式合并优化、响应式转换、单位规范、类型与规范校验。

06

代码生成

生成结构代码、样式代码、组件化输出、代码优化。

07

结果输出

输出可直接使用的前端代码、组件代码、样式文件与代码片段。

关键设计

  • 空间化重组：解决设计稿父子关系不明确的问题。
  • 架构分析：组件拆分、多 agent 并行生成，再拼接整体代码。
  • 数据收集：通过代码保留量评估 D2C 效果，支撑持续优化。

带来的价值

  • 提升还原效率，减少手动还原时间。
  • 提高还原质量，降低后续样式修复成本。
  • 提升组件复用，降低开发成本并缩短交付周期。

04 / Coding Strategy

代码生成：解决写不对、写不好、写不了

代码生成不是把需求丢给 AI 就结束，而是用澄清、拆分、胶水编程、蓝图和知识库共同约束它，让结果真正可落地。

Input

需求输入

用户提出业务需求，进入对话式澄清。

Clarify

需求澄清前置

通过一问一答收敛问题，降低理解偏差。

Split

架构拆分

拆分模块、组件和数据流，降低单次生成复杂度。

Glue

胶水编程策略

优先复用已有模块，用最少胶水代码组合、封装和适配。

Code

生成代码

基于澄清后的需求和架构生成工程代码。

Map

生成蓝图

生成架构图、数据流、字段溯源，校验 AI 理解是否符合预期。

Land

输出与落地

产出高质量代码并集成到项目中。

05 / Debug Collaboration

联调自测：从人工排查转向 AI 辅助定位

联调阶段最耗时的不是开发本身，而是问题定位、多方沟通、反复确认与修复。AI 适合处理日志、数据比对、错误归因和上下文关联。

常见阻塞

  • 接口字段不一致、数据结构变化。
  • 环境配置问题、状态异常难复现。
  • 前后端理解偏差、日志信息不完整。
  • 需要前端、后端、产品、测试多轮沟通。

未来探索方向

  • 接口异常分析：请求参数、返回结果、字段差异、状态码异常。
  • 日志与错误聚合：Console、Network、服务端日志形成问题摘要。
  • 问题归因辅助：判断前端、后端、配置或环境问题。
目标：减少重复沟通与低效排查，让研发更快聚焦真正的问题修复。
06 / Code Review

CR 阶段：让 Review 从看代码升级为风险分析

传统 CR 受 Reviewer 精力、上下文完整度和全局影响分析能力限制。AI CR 平台的目标是在上线前识别更深层风险。

01

代码提交

开发提交 PR/MR，触发 CR 流程。

02

AI 预分析

识别变更范围，生成初步分析报告。

03

人工 Review

Reviewer 查看 AI 报告，结合代码进行 Review。

04

问题确认与处理

确认问题，提出修复建议，标记误报或忽略说明。

05

结果汇总

生成 CR 结论、风险等级与评价。

06

上线决策

通过 CR 后合入主干，进入测试或发布流程。

当前核心能力

  • 增量分析：基于 diff 分析本次改动真正带来的影响。
  • 全链路影响分析：从局部到全局识别真实业务影响。
  • 效果反馈正循环：误报、漏报和人工处理结果持续回流。

未来方向：上线风险分析

  • 结合技术文档与架构设计理解业务背景。
  • 参考历史问题、风险案例和最佳实践。
  • 从“最后一道质量卡”升级为完整上线风险评估。

07 / Test Checklist

测试阶段：自动生成基于上下文的自测 Checklist

很多问题不是不会测，而是边界场景、异常流程、状态覆盖和回归范围容易遗漏。AI 可以把“凭经验自测”升级为“系统化检查”。

主流程检查确保核心业务路径完整可用。
边界场景覆盖极值、空值、缺省和边缘状态。
异常流程覆盖接口异常、状态异常和重试逻辑。
权限校验覆盖角色、可见性和操作权限。
状态切换检查多状态流转和 UI 反馈。
接口异常检查失败、超时、字段缺失和格式变化。
空数据场景检查空态、加载态和兜底文案。
回归影响范围结合变更识别需要回归的页面和模块。
最终实现：减少遗漏问题、提升自测覆盖率、降低低级 Bug、缩短测试沟通成本。
08 / After Release

发布后：AI 助力线上运营、巡检与知识沉淀

发布之后研发工作并没有结束。线上阶段更关注风险发现、问题定位、经验沉淀与长期可维护性。

知识库沉淀沉淀新路由、新工具、新组件、新业务能力和历史问题案例。
自动巡检结合发布时间与 CR 风险分析结果，自动触发线上巡检。
线上监控与问题分析整合告警、用户反馈、页面异常、日志与调用链路，辅助定位根因。
自主修复未来逐步完成配置降级、风险功能下线、异常状态恢复和修复方案生成。
沉淀与反馈分析结果自动沉淀，反馈知识库、风险模式和 AI 能力。

多源数据接入

  • 监控指标、日志数据、调用链路、用户反馈和业务数据。
  • AI 智能分析引擎负责关联分析、根因定位、模式识别、影响评估和趋势预测。

最终目标

  • 形成研发全流程的 AI 闭环能力。
  • 风险自动发现，问题自动分析，经验自动沉淀。
  • 部分问题自动修复，降低人工干预成本。

09 / Conclusion

结论：AI 提效的本质是工程能力升级

AI 在前端领域的价值不是替代单点工作，而是把研发流程中的经验、上下文和反馈机制产品化。

1

从“写页面”到“管理全生命周期”

前端研发已经覆盖需求理解、方案设计、开发联调、质量保障、发布运维和线上问题处理。

2

从“AI 生成代码”到“AI 理解工程体系”

通过规范、知识库、蓝图、组件映射与反馈闭环，让生成结果真正进入业务工程。

3

从“局部提效”到“流程闭环”

数据反馈持续优化 AI 能力，形成越用越智能、越用越高效的正循环。
